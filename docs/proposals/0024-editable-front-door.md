## Summary

Front doors stay editable. READMEs, badges and start-here links are never
pinned by a frozen identity. Frozen identities pin only normative bytes:
specifications, schemas, reference code, tests and AI instruction files such
as `SKILL.md`.

Today a README edit in this repository changes the Workspace/1 runtime
identity. This proposal:

- mints a successor manifest token, `rapp-workspace-file-manifest/2`, that
  pins only normative bytes;
- keeps the old manifest byte-for-byte as named, verified history;
- re-pins the `rapp-work-sdk/1` sidecar profile through the SDK's own
  forward-generation mechanism.

## Design decisions and alternatives rejected

**Decisions.**

1. **A successor identity, never a mutation.**
   `rapp-workspace-file-manifest/2` has exactly the `/1` key set plus
   `predecessors`. The `/1` label keeps meaning exactly the retained bytes.
2. **Normative bytes only, by an explicit allowlist plus a tripwire.**
   `repository_evidence` is an explicit tuple of normative repository files.
   The generator also walks every `path` the built manifest lists and refuses
   any front door, which catches regressions an allowlist review might miss.
3. **History is retained, verified and never regenerated.**
   - The `/1` bytes live at
     `protocols/rapp-workspace/1/history/f1165f947cb5d7554906012a174a854b28454403e41e8166925a364a68680370/manifest.json`.
   - The generator and every qualification check their SHA-256, length,
     schema label, `profile: "rapp-workspace/1"` and `status: "core"`.
   - A prototype manifest can therefore never be named as a predecessor (SPEC
     §2). The grail prototype reuses the `/1` label but fails the
     profile/status guard.
4. **The Workspace/1 SPEC stays byte-identical.** The contract (SPEC, safety
   matrix and schemas) does not change; only the runtime inventory does.
   Changing the SPEC would move `spec_sha256`, which the estate kit pins, for
   no semantic gain.
5. **The SDK is re-pinned by a new generation.**
   - Generation 3 is pin `e657140`, whose parent bytes are byte-identical.
   - `591e014` becomes `migration-source-only`, with its exact profile bytes
     retained.
   - The SDK's own `--write-parent-profile/--write/--write-index` path
     regenerates every SDK pin; nothing is hand-edited.
6. **The SDK file-manifest token stays.** Its key set, record grammar and
   hash rule are unchanged. It stops inventorying `reference/README.md` and
   gains the same front-door tripwire.
7. **The pinned AI instructions become self-contained.**
   - The three `SKILL.md` files no longer call READMEs verified and no longer
     delegate commands to them.
   - The `py_compile` command moves into `SKILL.md`.
8. **Generator defects this change exposes are fixed.**
   - Both generators' `--write-index` now replaces entries in place and
     keeps `generated_utc`.
   - `skill_locks.py` now sorts by path string.

   Both changes are byte no-ops on `main`'s committed files (verified in
   pristine copies).
9. **Skill locks are integrity inventories, not identities.**
   `tools/skill_locks.py` regenerates the `rapp/agent.lock.json` files, and
   their hashes change whenever any skill file changes. Nothing external
   binds them, and they are not RAPP/1 identities.

**Alternatives rejected.**

- **Mutate `/1` in place** (drop the READMEs, keep the label). One label
  would then carry two selection rules (Art. 2). Every `f1165f94` receipt and
  the SDK history would point at a hash with no retained bytes. The tests
  refuse this (M16).
- **Keep `/1`.** Front doors stay frozen, the badge and "Start here" stay
  blocked, and every README edit keeps orphaning stores and forcing SDK
  re-pins.
- **Pin READMEs in a separate "non-identity" inventory**, such as a README
  lock checked by CI. A red gate on a README edit is still a pin: under
  Art. 8 it is a finding that must be acted on, so front doors would still
  not be editable. It would also add a second pin surface with no owner.
- **Exclude READMEs only by glob, with no tripwire.** A later edit that
  re-lists a README would pass silently. The tripwire and tests catch this
  (M1, M2, M7, M8).
- **Mint `rapp-workspace/2`.** The protocol contract is unchanged, so a new
  protocol token would claim a semantic change that does not exist. Art. 2
  moves the token of the thing whose shape changes, which is the manifest.
- **Edit the SDK profile in place at `591e014`.** Every installed `591e014`
  sidecar would fail ("generation … profile bytes changed"), and SDK SPEC
  §§1–2 would be broken.
- **Use a fabricated or future SDK pin.** Identities are minted, never
  derived (Art. 7). The pin must be a real parent commit with verified bytes,
  and `e657140` is `kody-w/rapp-1` `main`.
- **Stamp `generated_utc` with the wall clock.** That makes the generator
  non-deterministic. The field is informational and unconsumed, so the
  generators now keep it and can no longer regress it.

## Proposed change

### Normative definition of the successor token (enforced by the reference)

This defines the token; it is not a SPEC edit.

> **`rapp-workspace-file-manifest/2`.** The Workspace/1 runtime manifest is
> a JSON object with exactly the members of `rapp-workspace-file-manifest/1`
> plus `predecessors`, in that order.
>
> - `normative` pins `SPEC.md`, `safety-matrix.json` and every
>   `schemas/*.json`.
> - `reference` pins every `reference/*.py`.
> - `repository_evidence` pins only normative repository bytes:
>   specifications, reference entry points, core tests and AI instruction
>   files (`SKILL.md`). It MUST NOT list a human-facing front door.
>
> A path whose final component, case-folded, is `readme` or begins with
> `readme.` is a front door. A generator MUST refuse to build a manifest that
> lists a front door anywhere.
>
> `predecessors` is an ordered list of retained predecessor manifests. Each
> entry is exactly `{schema, path, sha256, bytes}`, where `path` is
> `history/<sha256>/manifest.json` relative to the protocol directory.
> Generators and qualification MUST verify the retained bytes' SHA-256 and
> length, and that they declare `schema`, `profile: "rapp-workspace/1"` and
> `status: "core"`. They MUST NOT regenerate the retained bytes.
>
> A predecessor is lineage for inspecting history, never a current runtime.
> Qualification accepts only the current manifest bytes. Receipts and
> activation documents bound to a predecessor remain historical evidence
> (SPEC §11); new execution requires current qualification.

The successor's `repository_evidence` is exactly:

- `SPEC.md`
- `SKILL.md`
- `tools/frame_lens.py`
- `tests/test_safe_kernel.py`
- `tests/test_p0_hardening.py`
- `.github/skills/rapp-workspace/SKILL.md`
- `.github/skills/autonomous-rapp-estate-manager/SKILL.md`

## Token and compatibility analysis

  - The Workspace manifest's key set changes (`+predecessors`) and so does

    - `rapp-work-sdk-prior-release-fixture/1`: the new `fixture.json` has the

    - `rapp-skill-lock/1`.

- **Art. 4 (growth by registration).** No frame kind, envelope or door

- **Art. 8 (red oracles).**

  (`dda32d741c7218f41443a5bd17eebfe0eae82cb7`).

## Security and privacy analysis

**What an unpinned README can do.** It can change human-facing prose,
badges and links.

**What it cannot do:**

- Be read by any runtime. The kernel, qualification, the SDK scaffold, the
  skill wrapper and the Private Hive scripts do not import, hash or load any
  README.
- Grant authority. Authority comes only from the external `ExternalPolicy`
  and activation.
- Change qualification, SDK install or update, or any pinned byte.
- Instruct an AI through these skills. The pinned `SKILL.md` files now call
  READMEs unverified navigation and carry their own commands. Before this
  change they delegated "verified" API and commands to READMEs, which would
  have become an unpinned instruction channel. The same successor fixes
  that.

**What stays pinned.** Every normative byte, all reference code, the entry
tool, the core tests and all three AI instruction files. Editing any of them
changes the identity, and qualification refuses; tests prove this for 11
files.

**History integrity.**

- A tampered or missing retained predecessor makes pins and qualification
  refuse.
- A prototype manifest can never be listed as a predecessor.
- The SDK generator refuses to reseal over tampered retained profiles, and
  refuses to create displaced history from any other bytes.

**Residual risk.** Humans, and AIs not using these skills, may still follow
README commands. README edits are reviewed through git history and pull
requests rather than detected by pins. README claims fall under Art. 9
(claims are computed and dated).

**Privacy.** All fixtures are synthetic (`rappid:@fixture/…`,
`rappid:@fictional/…`, `example.com`). The receipt vector holds only the
deterministic synthetic demo data. There are no local paths, and the
repository privacy scan reports 0 findings.

**Fail-closed defaults are unchanged.** Live activation needs an
independently authenticated document, synthetic mode must be explicit,
external effects stay disabled, and old pins never auto-update.

## Migration

**Sidecars installed at `591e014`**, the previous current pin:

- They keep verifying: `verify` reports `current_pin: 591e014…` against the
  retained profile bytes.
- A same-workspace `install` refuses with "different pin requires an
  explicit update". That includes Private Hive `prepare` on an
  already-prepared workspace.
- The operator runs `scaffold.py plan-update --from-pin 591e014… --to-pin
  e657140…`, then `update … --plan-digest <exact digest>`.
- The update binds `from_profile_sha256 f9a1b773…` and the new target
  profile. It keeps the `591e014` generation byte-identical, never touches
  native bytes and uses no network.
- This is proven end to end with a real `591e014` sidecar produced by the
  unmodified `main` scaffold (`fixtures/prior-release-591e014/`), tested in
  both the unit tests and SDK conformance.

**Sidecars at `4b4fc213` or `1c0e0b7c`** update directly to `e657140…` under
the same rules. The legacy fixture and its tests are unchanged and pass.

**Workspace/1 controllers bound to `f1165f94`.** No estate activation exists.

- A synthetic store created under `f1165f94` refuses to reopen under the
  successor. With the successor policy it fails with
  `external-policy/configuration-substitution`; with the old policy it fails
  with `runtime-qualification-required`. The first was observed with a store
  left by the baseline demo; the second is tested.
- Its frames stay inspectable. `verify_historical_archive` verifies the
  15-frame export, 11 frames of which bind
  `runtime_sha256 = f1165f94…`, without touching the current runtime.
- New work uses a fresh controller directory, which the SPEC and README
  already require.

**Activation documents bound to `f1165f94`.** None exist. A future one would
need a new owner-issued document binding the successor hash. Nothing rebinds
automatically, and synthetic/live promotion stays refused (SPEC §4.1).

**Private Hive.** The `prepare_workspace.py` constants are rebound by
`tools/skill_locks.py --bind-private-hive`, never by hand.

## Rollback

- **Before merge:** don't merge the branch; nothing else changes.
- **After merge, before any sidecar is updated to `e657140`:** revert the
  merge commit. `f1165f94` becomes current again. Only synthetic stores
  created under the successor refuse to reopen, by the same mechanism, and no
  live activation exists.
- **After a sidecar has been updated to `e657140`:** sidecars cannot
  downgrade (SDK §4), and reverted code would treat `e657140` as unknown and
  fail closed. Roll forward instead, per Art. 3 ("the way out is always
  forward"): mint a further successor that retains both manifests as
  predecessors and keeps `e657140` as a migration source.

## Reference implementation and gating

The reference implementation exists only on
`experimental/gap-g24-editable-front-door`.

- **Nothing takes effect until the owner acts.** The successor identity
  applies only if the owner accepts this proposal and merges the branch.
  Until then `main` keeps `f1165f94…` and `591e014`.
- **No semantics change silently.** The Workspace/1 SPEC, safety matrix,
  schemas and `qualify()` are byte-identical. The change is limited to the
  manifest token this proposal defines, and to SDK profile data governed by
  the SDK SPEC's own replacement rule.
- **Defaults stay fail-closed.**
  - Old runtime pins refuse new execution.
  - Older sidecars are verified but never auto-updated.
  - A defect in retained history makes pins, qualification and resealing
    refuse.
- **Checks.** Every step of `.github/workflows/ci.yml` passes locally under
  Python 3.12, with a `dda32d7` RAPP/1 checkout and `TMPDIR` inside
  `.validation/`. GitHub CI runs on every push to this branch.

## Open questions for the owner

1. **Should the front-door rule go further?** The tripwire covers
   README-named files. The explicit allowlist already leaves every other
   unlisted file unpinned (for example `LICENSE` and `docs/`). Should badges,
   images or `START-HERE`-style files get a named rule as well?
   Recommendation: rely on the allowlist.
2. **Root `SPEC.md`.** It calls itself "navigation, not a second normative
   specification" (line 12), but stays pinned as a spec-class file. Should it
   become a front door? That would be a content change under `/2`, with this
   manifest kept as a second predecessor.
3. **SDK generation keys.** Because generations are keyed by parent commit,
   re-pinning a sibling needs a real new `rapp-1` commit. A future revision
   could key generations by profile digest instead; under Art. 2 that would
   be a new SDK token. This is recorded as an idea only.
4. **Archived README hashes.** Prototype catalogs
   (`prototypes/published/index.json` and the `grail-1.0` manifests) and
   `provenance.json` (the Frame Chains `README.md` and `evidence/README.md`)
   record README hashes as historical evidence. No gate re-verifies them, and
   no live front door feeds them. Recommendation: leave them as history.
5. **`generated_utc`.** The generators now keep this field unchanged. Is that
   acceptable, or should it be bumped to a dated value whenever the index is
   regenerated?
