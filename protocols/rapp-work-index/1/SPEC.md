# RAPP Work Index/1

**Profile:** `rapp-work-index/1`

**Status:** optional, additive application profile; not estate-activated

**Parent application:** `rapp-workspace/1`; **external authority:** canonical `rapp/1`

**Carrier:** the existing RAPP/1 `memory.save` kind

**Authority / grants:** false / none

## 1. Scope and precedence

MUST, MUST NOT, REQUIRED, SHOULD and MAY are normative requirements. This profile
defines bounded, exact, **non-authoritative acceleration** over supplied records.
It does not modify any RAPP/1 envelope, identity, particle/wave, signature,
registry, stream, capability, or canonicalization rule. It does not modify the
closed `rapp-workspace/1`, `rapp-hive/1`, or `rapp-federation/1` profiles.
Their published bytes remain independent. No new wire implementation is supplied.

RAPP-valid is not accurate observation, semantic fidelity, present authorization,
or safe deployment. A signed checkpoint attests an occurrence of a root commitment,
not the correctness, completeness, ownership, or authority of every indexed
claim. Neither an index, a hash, a valid proof, a full RAPPID, a successful query,
nor a cache entry grants a capability. Signed estate activation and all
authorization decisions remain external.

Deleting a database or shard MUST lose acceleration only. It MUST NOT delete,
replace, reset, merge, or manufacture source authority or the host's protected
checkpoint high-water mark. A missing/corrupt cache MUST explicitly refuse;
there is no silent source scan, automatic rebuild, downgrade, or first-wins
fallback. The caller MAY explicitly rebuild from supplied, verified bytes.

## 2. Trust and interpretation boundary

The caller MUST independently pin the intended canonical generation, external
policy/registry/key context, and source vector. At use time it MUST supply a
current frontier over a protected API. Index documents cannot populate that
API, the trust store, grants, registry selection, revocation state, or clocks.
If the caller cannot establish freshness it MUST refuse cached conclusions.

The runtime's `verified-frame` record is a **caller-supplied verification
result**, not a signed protocol, bearer receipt, or self-authenticating JSON
document. Its `signature_verified` and `chain_verified` constants are necessary
shape checks, never sufficient evidence. Only an independently installed
canonical RAPP/1 verifier, using externally selected signer/SPKI, stream,
chain head, registry/key epoch, and policy, may supply this record in a live
host. Parsing a downloaded/received record with these flags set is prohibited.
The pure unit tests explicitly use test doubles; they do not count as verified
RAPP/1 Frames.

The reference conformance adapter loads only the explicitly supplied canonical
checkout at the commit and exact file hashes in `provenance.json`. It checks
the canonical anchor chain and materialized normative text, then calls the
canonical implementation to construct, canonicalize, and verify actual signed
Frames. It never downloads or copies a wire implementation. Its deterministic
public test keys and synthetic policy/registry roots are not production trust.
Production registry authentication, revocation, protected high-water storage,
key custody, coherent source observation and deployment remain external.

## 3. Closed application data and exact bytes

`schema.json` is Draft 2020-12. Its objects are closed: all declared members
are required, undeclared members refuse, and booleans are not integers.
`$defs` names identify the subsidiary types, including `identity`, `context`,
`source`, `source-vector`, `descriptor`, `token` and `adapter`. The root
`oneOf` selects tagged public application records. Schemas are generated by
`reference/schema_source.py`; semantic checks below are also REQUIRED.

For these **application documents only**, canonical octets are ASCII JSON,
object keys sorted ascending, no insignificant whitespace or terminal newline,
unescaped printable ASCII except JSON-required escapes, and exact integers
in `[-(2^53-1), 2^53-1]`. Profile integer fields are unsigned. Floats, NaN,
duplicate object members, cyclic values, excess nesting, non-ASCII strings
and noncanonical equivalent encodings refuse. This narrow ASCII domain avoids
Unicode sort/normalization differences; it is not a replacement for RAPP/1 JCS.
Canonical RAPP/1 Frame octets are produced/verified only by the parent.
Pretty-printed inventory, provenance, safety and schema files are instead
pinned as their literal file bytes.

`domain` is a lowercase ASCII label, 1–64 characters, matching
`[a-z][a-z0-9.-]*`. `key` is 1–128 ASCII characters from `!` through `~`.
There is no trimming, case folding, prefix matching, fuzzy matching, locale
collation, URI expansion, filename inference, or default domain.

An index `record` has:

| Field | Meaning |
|---|---|
| `schema` | `rapp-work-index/1/record` |
| `domain`, `key` | Exact lookup domain and human/exact address |
| `rappid` | Full RAPPID, not a chant or short hash |
| `content_sha256`, `content_bytes` | Plain SHA-256 and count of the exact supplied content octets |
| `particle_hash` | Supplied canonical RAPP/1 content particle hash |
| `occurrence_hash` | Supplied canonical RAPP/1 Frame wave hash |

A full candidate identity comprises **all five fields from `rappid` through
`occurrence_hash`**. Candidate order is the ASCII tuple `(rappid,
content_sha256, particle_hash, occurrence_hash)`. Record order prepends
`(domain, key)`. Equal order tuples are duplicate candidates and MUST refuse,
even if another field differs. There is no first-record-wins import.
Full RAPPID syntax and owner/slug bounds (39/100) are checked, but syntax alone
does not authenticate identity, mint an identity, or assert key possession.

The source vector is an explicit list of at most 64 `source` objects sorted
by their unique `source` label. Duplicate `(subject, frame_hash)` occurrences
also refuse. Each source binds subject, exact content digest/length,
signer/SPKI digest, stream/seq, payload/frame hashes, raw Frame SHA-256,
key/registry epochs, policy root and registry root. Every record MUST match
one source's subject/occurrence and exact content digest/length/particle.
This consistency check does not substitute for validating the canonical
source Frame and its current rights before source consumption.

## 4. Deterministic shards and Merkle commitment

There are exactly **16 shards**, numbered 0–15, including empty shards.
A key bucket never spans shards. Its shard number is:

```text
q = canonical({"domain": domain, "key": key})
shard = first_octet(SHA256(ASCII("rapp-work-index/1:key") || 0x00 || q)) mod 16
```

A shard is the canonical closed object
`{"schema":"rapp-work-index/1/shard","shard":number,"records":[...]}`.
Its records are in strict record order; count is at most 256. The shard has
no generation, timestamp, platform, location, or policy field. Therefore
unchanged content shards can be reused across different signed occurrences.
Keys MUST NOT be used as filesystem paths.

Let `raw[i]` be the exact shard bytes, `h[i] = SHA256(raw[i])`, and `len[i]`
their byte count. All hashes in documents are lowercase 64-hex strings.
Hash inputs below contain **binary 32-byte digests**, not their hex text:

```text
leaf[i] = SHA256(
  ASCII("rapp-work-index/1:leaf") || 0x00 ||
  unsigned_big_endian_16(i) || unsigned_big_endian_64(len[i]) || h[i])
node(L,R) = SHA256(ASCII("rapp-work-index/1:node") || 0x00 || L || R)
```

Pair adjacent nodes in numeric shard order, for exactly four levels. The
single remaining hash is `root`. There is no odd-leaf duplication, padding,
platform salt, host path, native database page hash, or implicit empty tree.
Position and length are part of each leaf; leaf and node domains are distinct.

A `generation` manifest binds `generation` (uint53), root, context, source
vector, all sixteen descriptors, aggregate item/byte counts, and
`authority:false`. Every descriptor binds numeric shard, plain exact-byte
hash/count, item count and leaf hash. Descriptors MUST cover 0–15 exactly and
in order. Leaf hashes, Merkle root, counts and bounds MUST be reproduced.
The manifest's **plain SHA-256 over its canonical bytes** commits the complete
generation; the Merkle root alone commits only shard content.

A `proof` binds manifest SHA-256, root, shard number, leaf hash and exactly
four sibling hashes, bottom-up. Left/right position derives from successive
low bits of the shard number; an input cannot select the side. Verification
MUST check the exact manifest/root, size, raw SHA-256, leaf, all siblings,
resulting root, canonical shard bytes, placement, count, ordering and source
bindings. Missing proofs, partial trees, corrupted bytes, substituted positions,
wrong-generation proofs and excess counts refuse before use or storage.
Possession of all descriptors permits reproducing a proof; it never excuses
the API's explicit proof requirement or the content checks.

## 5. Signed checkpoint roots and monotonicity

The manifest's closed `context` binds:

- externally selected signer full RAPPID, SHA-256 of DER SPKI, stream;
- key epoch and registry epoch;
- registry, policy, grant, revocation and subscription roots;
- a context root distinguishing the intended contextual use.

These are explicit external commitments, not policies interpreted or fetched
by the index. A `memory.save` checkpoint payload is the closed
`rapp-work-index/1/checkpoint` object: generation, manifest SHA-256, shard
root, SHA-256 of canonical context, SHA-256 of canonical source vector, and
`authority:false`. The unchanged canonical RAPP/1 Frame supplies stream,
sequence, particle hash, wave hash and signature.

The caller-supplied verified record MUST identify `memory.save`, carry the
exact payload, complete context and occurrence fields, and attest both
signature and canonical stream-chain verification. Occurrence fields are
signer, SPKI digest, key/registry epochs, stream, seq, payload hash, wave
hash and SHA-256 of the **entire exact signed Frame bytes**. The last field
also binds signature bytes, which a wave hash alone does not bind.

`bind_checkpoint` compares the complete expected external context, every
repeated signer/stream/epoch field and the exact checkpoint payload, and
constructs a closed `binding`. `validate_checkpoint_binding` additionally
compares a supplied stored binding with that derived record. A signature
over a different manifest, context, source vector or root is insufficient.

The host MUST retain its accepted high-water binding **outside disposable
index storage**. The first external trust decision may bootstrap a pinned
generation; absence of a cache is not permission to bootstrap again.
Every later candidate MUST be checked against the protected previous binding:

1. Different stream: refuse; an independently authenticated new lineage is
   a separate host action, not an automatic cache transition.
2. Lower sequence: rollback, refuse.
3. Same sequence, different root: fork, refuse.
4. Same sequence, any other binding difference: occurrence/generation fork,
   refuse. The exact same binding is an idempotent replay, not a renewal.
5. Higher sequence: require a strictly greater generation, a different wave
   hash, and nondecreasing key and registry epochs. External canonical
   verification MUST already establish the chain, including any intervening
   Frames; the index does not reconstruct or invent skipped wire history.

Rotation or changed roots require a newly independently verified occurrence
and externally current context. The reference never automatically follows a
key, registry entry, subscription, policy, grant, stream, or remote root.

## 6. Cache invalidation and exact lookup

`PinnedGeneration` snapshots canonical manifest, binding and frontier bytes;
its public values are copies. The frontier binds the complete context and
source vector, manifest SHA-256, checkpoint wave hash and exact Frame
SHA-256. Every query, summon, shard acceptance, anti-entropy comparison and
cache-key use MUST compare a freshly supplied host frontier against it.
The comparison MUST include all fields; partial freshness is not freshness.

The generation fingerprint is
`SHA256("rapp-work-index/1:generation" || 0x00 || manifest_bytes || binding_bytes)`.
A raw-byte cache key is
`SHA256("rapp-work-index/1:cache" || 0x00 || SHA256(raw) ||
uint64be(len(raw)) || generation_fingerprint)`.
Thus raw bytes, signer/SPKI, stream, key/registry epochs, policy/checkpoint/
grant/revocation/subscription/context roots, complete source vector, and
exact occurrence bytes are bound. Rotation, revocation, new grants, changed
roots or subscriptions, source substitution, or a new wave invalidate old
cached conclusions even if content and Merkle root are unchanged.

`pin.frontier` is a **comparison value**, not evidence of present freshness.
Live code MUST NOT manufacture "current" input by copying it from a stale
cache or received index. The conformance uses this value only inside its
explicit fixed synthetic host context. A cached validation result cannot
be converted into an authorization grant.

The reference SQLite store uses three closed `WITHOUT ROWID` tables:
metadata, shards/proofs and records. The record primary key is
`(domain,key,rappid,content_sha256,particle_hash,occurrence_hash)`, using
binary collation. Content byte count, shard number and canonical record
bytes are stored as values. No unique short-name index may discard collisions.

Build accepts only a complete, bounded set of verified shards/proofs, inserts
them transactionally into a newly and exclusively created database, and
refuses an existing destination. Open uses an explicit caller-owned path and
a read-only transaction. Before serving anything it checks the exact table
layout (including absence of foreign views, triggers or indexes), metadata,
page/count bounds, SQLite integrity, every shard/proof and **every derived
row**, including omissions/extras. It then retains that verified read snapshot.
Unknown journals/WAL/SHM files refuse instead of automatic recovery. A partial
failed build remains unusable until an explicit discard/rebuild; no repair is
silently inferred. File/index corruption is never repaired by changing source
identity or the externally pinned root.

SQLite page bytes are adapter-local, not canonical protocol data.
Reopen/recovery verification is **O(n + total bytes)**. After that bounded
verification, durable exact/keyset lookup uses the B-tree:
**indexed O(log n + returned candidates)**. Cursor boundary checking can
also examine the bounded key bucket. Python's process-local source dictionary
may be described only as **expected O(1)** per exact lookup, excluding
construction/validation and adversarial worst cases. There is no global O(1),
unmeasured latency, universal constant-time, or global incremental-delta claim.

## 7. Continuation tokens

A continuation is an opaque, deterministic, unpadded canonical base64url
encoding of `{"cursor":cursor,"checksum":digest}`. The checksum is
`SHA256("rapp-work-index/1:cursor" || 0x00 || canonical(cursor))`.
`cursor` binds schema, generation, complete manifest SHA-256, Merkle root,
SHA-256 of the complete binding, checkpoint wave, exact domain/key, shard,
the final **full candidate identity**, and page size (1–64). The complete
manifest/binding pins transitively include all external context and sources.

The receiver MUST check canonical encoding, checksum, closed shape, full
generation/binding/domain/key/shard/size equality and the exact cursor identity
in the verified snapshot. That identity MUST end a full page (its 1-based
rank is a multiple of page size) and have a successor. Missing, substituted,
terminal and nonboundary cursors refuse. A keyset query starts strictly after
the full final order tuple; it does not use an ambiguous short key or unstable
offset. Only nonterminal pages emit tokens.

Changing a root, generation, checkpoint, context, source vector, key domain or
page size invalidates the token. There is no "best effort" resumption in a
different snapshot, which could skip or duplicate candidates. Reusing the
same token in the same snapshot intentionally returns the same page; this is
not an exactly-once delivery protocol. The checksum is **not a MAC**, secrecy,
proof of cursor issuance, or capability. A caller may deliberately select
another valid page boundary; authorization must not depend on this cursor.

## 8. Summon collision buckets

Chants, slugs, short hashes and repository names are human addresses, not
proof. All matching full candidates MUST remain in deterministic order,
including different identities sharing a chant and multiple content/occurrence
candidates for one full RAPPID. **"First repository wins" is prohibited.**

`summon` requires the exact domain/key, all five full identity fields and
explicitly supplied content bytes. It verifies the byte hash/count and the
exact candidate row. No filename, repo ordering, convenient first result,
identity prefix or substituted same-named content may disambiguate.
The result is `disambiguated-not-authorized`, `authority:false`.
Source verification, current policy and capability checks still precede
source use. A collision bucket exceeding the fixed bounds refuses rather
than silently truncating, repartitioning or selecting a winner.

## 9. Pinned anti-entropy, not authority merge

Both local and target generations MUST already be separately pinned through
the external verification boundary and checked against supplied current
frontiers. Target transition checking rejects rollback/fork. No remote
manifest or inventory can install its own trust.

Compare numeric descriptors and at most sixteen explicitly supplied local
byte strings. A closed report includes:

- `changed`: every differing local/target descriptor hash, with exact hashes;
- `missing`: every absent supplied shard and its exact target hash;
- `divergent`: every supplied shard not matching the target, with the local
  descriptor, actually observed, and target hashes;
- `available_needs_proof`: byte hashes that match, still not accepted by
  this comparison alone.

A report is a bounded request description, not permission to fetch, merge
authority, infer consent, or execute anything. `accept_shard` accepts only
explicit bytes and an inclusion proof against the target pin, repeating all
hash/canonical/proof/source checks. Even an unchanged shard needs a proof
bound to the selected complete target generation. There are no network
clients, recursive fetches, subscription polling or automatic peer selection.

## 10. Platform adapters and sleeping organisms

All adapters operate over identical canonical shard bytes, source vectors,
checkpoint bindings and root/proof algorithms. Adapter names, native pages,
storage keys and filesystem metadata MUST NOT change roots or weaken checks.
`platform_adapters()` returns closed descriptors, not an activation command.

| Adapter | Storage and optional acceleration | Qualification |
|---|---|---|
| POSIX / macOS / Linux | SQLite `WITHOUT ROWID`, explicit regular files; optional verified safe copies, APFS clones or filesystem reflinks | Reference SQLite and no-follow filesystem I/O implemented; cloning optimizations not implemented |
| Windows | SQLite with the identical binary keys; explicit safe-copy replacement; optional ReFS block cloning | Mapping only; reparse-point, hardlink, locking and durability checks require a qualified host adapter |
| Browser | IndexedDB exact compound keys/byte blobs, OPFS shard bytes, WebCrypto SHA-256 and supported signature verification | Mapping only; canonical RAPP/1 signature/registry/chain semantics must remain externally verified |

POSIX reference I/O walks explicit directories with no-follow descriptors,
uses bounded regular-file reads with stable descriptor/name checks, and
rejects hardlinks/symlinks and group/world-writable database parents. It assumes
an independently protected caller-owned path, trustworthy OS/SQLite, and no
hostile same-UID writer racing its SQLite connection. These checks are not a
claim of coherent live source capture or a filesystem security sandbox.
Unsupported safe I/O primitives refuse; there is no weaker portable fallback.

Windows optimizations MUST verify copied/cloned exact bytes before publication
and maintain equivalent no-reparse, ownership, snapshot and crash constraints.
ReFS availability is optional, not a claimed dependency or benchmark.
Browser adapters MUST retain canonical byte arrays rather than trusting
platform JSON serialization, normalize neither keys nor identities, and
verify transaction/snapshot completeness. IndexedDB/OPFS quota or eviction
loses acceleration only. Unsupported WebCrypto algorithms MUST refuse, not
substitute unsigned hashes. Browser storage cannot hold the only security
high-water mark.

Sleeping organisms require **zero resident process, zero polling and zero
network**. Work is explicitly invoked, finite and foreground/on-demand.
A service, browser worker or background scheduler is not required. Adapters
must not activate one as a side effect of loading data.

## 11. Resource ceilings and failure behavior

The reference enforces these per-generation / per-open-operation-context
ceilings; a host MAY lower them, not silently expand the profile:

| Resource | Ceiling / behavior |
|---|---|
| Shards / queue | 16, complete including empty; no unbounded producer queue |
| Items | 256 per shard; 4,096 total; a producer is consumed only up to the first excess item |
| Shard / generation bytes | 256 KiB per shard; 4 MiB total |
| Record / manifest bytes | 2,048 / 128 KiB |
| Source vector / content | 64 sources; 1 MiB per explicitly supplied content or canonical Frame |
| Proof / page / cursor | 4 siblings; 1–64 candidates; 4,096 encoded token characters |
| JSON work | depth 16, 100,000 visited nodes, bounded containers/strings, no numeric expansion |
| SQLite | 4,096-byte pages; at most 4,096 pages / 16 MiB; 2 MiB page-cache target, mmap off, memory temp store, extensions off |
| SQL work | 5,000,000 VM steps per connection; bounded SQL text/columns/variables/expression depth; attached DBs disabled |
| Queries | 256 calls per opened snapshot, including refused query attempts after freshness; explicit lower ceiling supported |
| Files / disk | one DB plus at most its rollback journal during creation (provision at most 32 MiB); no automatic retained generations; profile inventory at most 128 files / 8 MiB / 512 visited directory entries |
| Explicit paths | at most 64 components / 4,096 encoded bytes; no parent traversal or ambient discovery |
| Streaming / expansion | file reads in chunks at most 64 KiB; bytes/count checked before and during reads; no compression, archives, nested index traversal, network or executable content |

Buffered shards, rows, proofs, source maps and result queues have both count
and byte ceilings. Python/SQLite object and allocator overhead is not an
asserted hard RSS value; a deployment requiring hard memory/disk/work limits
MUST additionally enforce host quotas. Aggregate multi-call workflow, retention
and concurrent-build budgets belong to the external host; opening a new
snapshot MUST NOT secretly reset its high-water mark or workflow budget.
The reference does not launch background workers or retry indefinitely.

This intentionally finite design is suitable for evaluation on **potato-class**
hosts without claiming unmeasured latency, throughput, energy use or minimum
RAM. Overflow, interruption, lock contention, unsupported adapter, malformed
input and exhausted work all refuse explicitly. Error handling MUST NOT
discover another source, read the home directory, fetch a URL, expand an
archive, adopt private paths, execute received code, or relax verification.

## 12. Particles, waves and contextual pivots

Content particles may be reused. Contextual occurrence and authority identity
MUST NOT be collapsed into content identity. A pivot in policy, context,
subscription, registry/key state or source selection requires a **new signed
checkpoint wave occurrence** before serving that generation. An unchanged
content root is not a renewal, grant or new contextual event.

The fixture includes two signed source occurrences sharing one particle but
different waves, six full RAPPIDs sharing the same human chant, and two
signed checkpoint generations with the same content root but different
context and waves. Their bindings and cursors differ. The signatures attest
these public synthetic occurrences only; neither wave activates an estate.

## 13. Conformance and exact distribution

The normative profile, schema, safety matrix, provenance, reference, tests,
requirements, documentation and public fixtures are exact-byte inventoried
in `manifest.json`. The manifest excludes itself and interpreter bytecode.
`protocols/index.json` pins specification, schema, manifest, safety matrix
and provenance hashes **and byte counts**, with authority false and activation
not-activated/external-host-only. Generated timestamps use the fixed branch
convention `2026-09-17T21:36:39.234Z`, never the executing host's clock.

From the repository root:

```bash
python3 -B tools/work_index.py schemas --check
python3 -B tools/work_index.py vectors --check
python3 -B tools/work_index.py pins --check
python3 -B tools/work_index.py tests
python3 -B tools/work_index.py conformance --rapp1-path "<EXPLICIT_RAPP1_CHECKOUT>"
```

The final gate is blocking: all tests must run without skips/errors/failures,
at least one test and one real RAPP/1 Frame must be verified, and exact input
pins must remain unchanged. The fixture currently emits and independently
re-reads/verifies **nine signed canonical Frames**, including two checkpoints.
Reports and a disposable exact index are written only under the explicitly
owned `.validation` output. Pure tests or application-vector checks reporting
zero verified Frames are useful partial checks, **not conformance**.

Fixture/signature tooling needs the canonical verifier's `cryptography`
dependency; the index runtime itself is stdlib-only. Missing canonical
checkout/dependency is a blocker, never an unsigned or invented-wire fallback.
Use the README's explicit generation commands after intentional profile
changes; changing pins does not authorize changes to closed sibling bytes.
